# Vicegerent Agent Instructions

Vicegerent is the infra-agent platform: credential-isolated, egress-locked, harness-agnostic agent sandboxes on a local Kind cluster (Cilium CNI), installed by a staged Helm script. The same hardened sandbox runs whichever coding agent you point it at (Hermes, Claude Code, Codex, OpenCode); the git repo is named `vicegerent-agents`; everything inside it uses the name `vicegerent`.

## Always

- **Don't merge** — open a merge request and let a human review and merge it.
- **Run pre-commit hooks** before every commit: `pre-commit run --files <changed files>`. Hooks: `check-merge-conflict`, `check-yaml`, `trailing-whitespace`, `end-of-file-fixer`, `check-added-large-files`, `detect-private-key`, `yamlfix`, `detect-secrets`, and the local `validate-manifests` (`scripts/validate.sh`).
- **Verify rendered output** before committing: run `scripts/validate.sh` — it layers `values.defaults.yaml` under the machine values per chart, exactly as the installer does. To hand-render a chart pass both layers (`helm template charts/platform -f values.defaults.yaml -f values.example.yaml --set-file secretPatterns=images/mcp-cerbos-shim/internal/server/secret-patterns.json`; the platform and egress-proxy charts both `required`-guard `secretPatterns` and refuse to render without that `--set-file`, and the agent/egress charts take the sliced equivalents `validate.sh` builds, since a bare `charts/*/values.yaml` is now empty). For a chart that renders a ConfigMap another workload consumes (the cerbos policies, the shim mapping), confirm that ConfigMap renders as intended.
- **Create MRs fully via the GitLab MCP tools or API** with a full, accurate description and a "Follow-up tasks" section for deferred work.
- **Omit values that merely restate a default; keep every values file minimal.** For upstream controller charts (`stages/values/*`), don't duplicate the chart's own defaults — link to the upstream default values file near the top. For the platform's own config, the committed `values.defaults.yaml` (repo root) is the single annotated default layer, layered *under* the machine `values.yaml` by the installer and `scripts/validate.sh` (`helm -f <defaults-slice> -f <machine-slice>`); the machine `values.yaml`, `values.example.yaml`, and `examples/*` carry **deltas only** (drop anything equal to a `values.defaults.yaml` default), and the in-repo `charts/*/values.yaml` are intentionally empty pointer files — don't put defaults back in them.
- **Wait for CI to pass** before declaring an MR done.
- **Ensure every image is Renovate-compatible** — use a fully-qualified image reference with an explicit tag (not `latest`, not a frozen digest) so Renovate can detect and propose updates. `Sandbox` and `AgentgatewayParameters` images are tracked by `custom.regex` managers in `renovate.json`.
- **Bump the image tag whenever the image content changes; never `imagePullPolicy: Always`.** Every image we build under `images/<name>/` (`hermes`, which builds the `hermes-agent` image, plus `agentgateway-proxy`, `mcp-cerbos-shim`, `aws-api-mcp-server`, `aws-profiles-mcp`, `kubernetes-mcp-server`) is deployed on a static, immutable tag and pulled under the default `IfNotPresent` policy — do not set `imagePullPolicy`/`pullPolicy: Always` anywhere, and never a floating or `latest` tag. Because `IfNotPresent` will not re-pull a same-tag rebuild, any change under `images/<name>/` that alters what the image contains (Dockerfile, build context, `patches/`, pinned tool versions) MUST bump that image's tag in the *same* MR — updating both the `TAG` default in `images/<name>/Makefile` and every manifest that references it (`values.defaults.yaml`'s `agents[0].image.tag` for hermes-agent, `charts/platform/templates/gateway.yaml`, `charts/mcp-cerbos-shim/templates/deployment.yaml`, `host/mcp/toolhive-servers.json`) — and the operator then runs `make -C images/<name> release TAG=<new>` to build and push before the rollout. A static tag that changes on every content change is the only mechanism that guarantees the new image is actually deployed, and `scripts/validate-image-tags.py` enforces both halves — statically that every deployed reference matches its Makefile `TAG` (run by `scripts/validate.sh`), and against the MR base that a build-context change came with a `TAG` change (the `validate:image-tag-bump` CI job). The two images built from an upstream release — hermes-agent and agentgateway-proxy — keep that upstream version as the tag's base and append a monotonically incrementing rebuild counter, `v2026.7.20` → `v2026.7.20-rev1` → `v2026.7.20-rev2`, resetting to `-rev1` when the upstream version bumps; both are matched by the `versioning: loose` rule in `renovate.json` so the suffix stays ordered instead of being read as a semver prerelease.
- **Slack Socket Mode recovery: the reconnect path itself can wedge.** `_restart_socket_mode()` holds `_socket_reconnect_lock` while awaiting `handler.close_async()`, whose CLOSE-frame write blocks for the whole kernel retransmit window (`tcp_retries2=15` ~= 800s+) on a black-holed socket — parking the watchdog loop and stranding the lock, so the adapter logs one "unhealthy" line and then goes deaf until a pod restart. `slack_sdk`'s own `monitor_current_session()` wedges the same way because its staleness check sits *after* an unbounded `session.ping()`. Bound both. When adding a liveness signal, key it on the SDK's `last_ping_pong_time` (advances every `ping_interval` regardless of chat traffic), **never** on inbound messages: `message_listeners` only fire for `WSMsgType.TEXT`, so a quiet DM looks identical to a dead socket and a traffic-based threshold reconnect-storms.
- **Keep the GitHub and GitLab Cerbos policies in lockstep.** `charts/cerbos-policies/policies/resource_gitlab.yaml` is a deliberate mirror of `resource_github.yaml`: the two forges get the same guardrails, and GitLab being a self-hosted instance the operator owns is a reason to get its policy right, not a reason to enforce it less. When you add, change, or remove a rule on one side — a new deny, a new attr, a `force` block, a live-resolved ownership gate, a capability dropped from the tool allowlist — do the same on the other side **in the same MR**, or state in the receiving policy's header comment why the rule has no analog there. The only legitimate reasons for divergence are a capability the other forge's tool surface genuinely doesn't have, or a rule encoding a work process that exists on one forge only (the `moveworks-emu/k8s-manifests` ticket-reference/change-link rules are the standing example); "we care less about GitLab" is not one, and no doc in this repo should say otherwise. Both policies' headers carry their current not-ported list — update it rather than letting the two silently drift.
- **Name the real provider in rendered Hermes config, never `custom`, or cost attribution silently dies.** `usage_pricing.resolve_billing_route()` maps `custom`/`local` to `billing_mode="unknown"` unconditionally, and an `unknown` route means `cost_status="unknown"`, no `session_model_usage` cost, and no cost line in the Slack runtime footer — a billing hole that presents as a cosmetic display quirk. `charts/agent/templates/_helpers.tpl` used to render `fallback_providers[0].provider: custom`, so **every failover session was unbillable** regardless of the price table. Naming the real provider (`anthropic`/`openai`/`deepseek`/`zai`) costs nothing: `resolve_provider_client()` passes `explicit_base_url` through for every provider name, so the agentgateway route is preserved identically (verified live for all four). Being priced needs BOTH halves — a price entry **and** a `resolve_billing_route()` branch; a provider with entries but no branch is priced on paper and unbillable in practice (deepseek shipped 4 entries with no branch until patch 0043 added one). `scripts/validate-model-pricing.py` (run by `scripts/validate.sh`) renders every provider/failover/mnemosyne permutation and asserts both halves for every model the chart can reach, so this cannot regress silently. Model prices themselves have exactly one source of truth: `images/hermes/patches/0043-model-pricing.py`, which fans one table out to both of Hermes' unsynchronized price sinks (`agent/usage_pricing.py` for live billing, `agentburn/prices.py` for `burn_report`) — never hand-edit one sink alone.
- **The sandbox blocks pushes to `main`/`master`/`production` client-side, and the PATH wrapper — not `/etc/gitconfig` — is what keeps it armed.** `images/hermes/git-guard/` bakes a root-owned `/etc/gitconfig` (`core.hooksPath`), a hook dispatcher, and a `/usr/local/bin/git` wrapper, all on the read-only rootfs so uid 10000 cannot edit them. The non-obvious part: `/etc/gitconfig` is *system* scope, which git ranks **below** worktree/local/global/`$XDG_CONFIG_HOME` config, so it can never hold on its own. Two things close that: the chart owns `~/.gitconfig` as a **read-only ConfigMap mount** (`charts/agent/templates/gitconfig.yaml`) carrying identity *and* `core.hooksPath` — global scope outranks XDG, so one file denies both global rungs, and it replaced the imperative `git config --global` seed that was the only reason the global rung was ever writable — and the wrapper re-injects `-c core.hooksPath=…` at **command scope** (the only precedence above every config file) for the repo-local/worktree scopes a mount cannot reach. **The mount, not the file mode, is what protects it:** git rewrites config via lockfile + `rename(2)`, so `chmod 444` is hijackable (verified: inode changes) while a ro bind mount refuses both `EROFS` write and `EBUSY` rename-over even under a writable parent. `scripts/validate-gitconfig-immutable.py` (in `validate.sh`) asserts the ConfigMap pins `core.hooksPath`, the mount is `readOnly`+`subPath`, and no container runs `git config --global`. It also expands aliases before classifying the subcommand (git expands a non-shell alias in-process, so `alias.x = push --no-verify …` would otherwise skip every check), matches config keys case-insensitively (git does), clears the whole `GIT_CONFIG_*` family including `SYSTEM`, and resolves the current branch through the caller's own `-C`/`--git-dir`/`--work-tree` options. `core.hooksPath` **replaces** `.git/hooks` instead of merging, so the dispatcher must keep chaining to the repo's own hook — and must spool `pre-push` stdin, since the guard consumes the ref lines the repo hook needs — or every repo's `pre-commit`/`pre-push` silently stops running. Changes here must keep `git-guard/test-git-guard.sh` green (64 cases, build-time smoke test, asserted against the bare remote's refs rather than push exit status; five of them pin the property that PATH-shadowing, a shell function named `git`, the `/usr/lib/git-core/git` hardlink, and GitPython skip the wrapper but NOT the hook) and keep the branch list in step with the `deny-protected-branch` rules in `charts/cerbos-policies/policies/resource_{github,gitlab}.yaml`. This is an accident interlock, not a security boundary — `/usr/bin/git` plus a writable global config is a known, documented bypass, and forge-side branch protection is the real enforcement.
- **Default to secure** — non-root, no privileged containers, `automountServiceAccountToken: false` where possible, least-privilege RBAC, secrets applied as Kubernetes Secrets by the setup scripts (never hardcoded in the repo; the installer never creates secrets).

## Repo Conventions

- **`values.yaml` is user-config, `charts/` + `stages/` are the platform.** Things a user changes to define an agent/model/MCP live in the gitignored `values.yaml` (the `agents:` list, cluster vars — deltas over the committed `values.defaults.yaml`) and in `charts/platform` (gateway, models, mcps, searxng, host-firewall); the standardized controllers (cilium, metrics-server, reloader, agentgateway, agent-sandbox, cerbos, victoria-logs, velero, tetragon) are installed from upstream charts pinned in `stages/stages.yaml`. The in-repo platform charts are `charts/{platform,cerbos-policies,mcp-cerbos-shim,agent,egress-proxy}`.
- **The layout is the documentation.** A user creates a new agent by adding an entry to the `agents:` list in `values.yaml`, and a new model/route by copying a template under `charts/platform/templates/models/`. MCP servers are not in the cluster tree — they run host-side under ToolHive and are declared in `host/mcp/toolhive-servers.json` (the cluster carries only `charts/platform/templates/vmcp.yaml`, which fronts the host vMCP with one backend/route/policy trio per Gateway listener: `vmcp` for agent traffic and `vmcp-internal` for the shim's own re-entrant lookups). Note that `service_names` on the ext_mcp wire carries the MCP **target** name (`spec.mcp.targets[].name`), not the `AgentgatewayBackend`'s `metadata.name`, and both trios front the same host vMCP under the target name `vmcp` — so a re-entrant lookup is indistinguishable from agent traffic by backend name alone, and shim code must identify its own calls by the secret self-token instead. Keep names self-explanatory and do not add explanatory comment blocks — rationale goes in the MR description, not inline.
- **One clone, one machine.** Each machine is its own clone with its own gitignored `values.yaml` and its own `kind-vicegerent` cluster; `charts/` + `stages/` + the committed `values.defaults.yaml` stay the shared, machine-agnostic platform. `values.yaml` (copied from the deltas-only `values.example.yaml`) holds only what differs from `values.defaults.yaml` — machine-specific cluster vars plus the `agents:` list. Nothing machine-specific lives in git. Stand up another machine by cloning again, copying `values.example.yaml` to `values.yaml`, editing it, and running `./vicegerent setup cluster && ./vicegerent setup secrets platform && ./vicegerent install`.
- **Aggressive cleanup is expected.** Delete redundant config, comments, examples, and docs instead of preserving them out of habit. Default to **no comment** on config that's self-explanatory from its field name/value (e.g. `strategy: RollingUpdate` needs no comment saying it's a rolling update). Only add a comment when it prevents a likely operational mistake or explains a genuinely non-obvious gotcha (e.g. a CNAME chain requiring intermediate FQDNs in an allowlist) — and even then, one terse line, never a multi-line block. Remove values that merely mirror Kubernetes, controller, chart, or language defaults after verifying the default from the upstream source. Conversation, history, and agent/tool-specific notes belong in the MR, not the repo.
- **Naming** — the project, cluster, and kube context are all `vicegerent` (context `kind-vicegerent`); the shared agent namespace is `agent-sandbox`. Only the git repo keeps the `vicegerent-agents` name.
- **No vendor directories for cluster infra** — controller charts are pulled by the installer via `helm upgrade --install <repo>/<chart> --version` (chart coordinates and pinned versions live in `stages/stages.yaml`); never commit upstream chart source. The exception is `csi-driver-host-path`, whose upstream deploy pulls sidecar RBAC from five sibling repos at apply time, so its manifests are vendored under `stages/kustomize/csi-driver-host-path/` and applied via `kubectl apply -k`; the snapshot CRDs/controller are still sourced upstream from `external-snapshotter`.
- **Storage/backup** — the agent `data`, `gitrepos`, and `models` PVCs all use the `csi-hostpath-sc` StorageClass, hardcoded (not values-driven) in `charts/agent/templates/pvc.yaml`, so Velero CSI-snapshots them. `vicegerent setup cluster` deletes kind's auto-installed local-path-provisioner and `standard` StorageClass right after cluster creation (no config flag skips it, kubernetes-sigs/kind#3176 is still open), and `csi-hostpath-sc` (`stages/kustomize/csi-driver-host-path/storageclass.yaml`) carries `storageclass.kubernetes.io/is-default-class: 'true'` so it becomes the new cluster default once `./vicegerent install` runs the `storage` stage.
- **Secrets model** — plain Kubernetes Secrets are the source of truth for cluster secrets (Kind etcd). No secret values live in git; the setup scripts (`scripts/install/setup-secrets-platform.sh`, `setup-secrets-agent.sh`) generate crypto material (CAs, certs, SSH keys, random tokens) and read user-supplied API keys from the environment or prompts, then `kubectl apply` the Secrets directly. MCP-server API keys are the exception — they are `thv` (ToolHive) secrets on the host, not Kubernetes Secrets (see `host/mcp`). Secrets are treated as disposable/recreatable — re-run the scripts to reseed a fresh cluster, and keep your own copy of any API keys elsewhere. The ghostunnel CA *key* lives only on the laptop under `~/.vicegerent/ghostunnel` and never enters Kubernetes (it only signs new certs). The server cert+key and CA cert ARE mirrored to a `ghostunnel-server` Secret so a host missing them recovers before ghostunnel starts (`vicegerent mcp` `ensure_ghostunnel_material`); the cluster also gets the client cert (Secret) and CA cert (ConfigMap). Trust the published CRD behavior (e.g. `caCertificateRefs` resolves to a ConfigMap keyed `ca.crt`, not a Secret).
- **Soft-wrap prose in Markdown docs** — one physical line per paragraph, list item, and blockquote; do not hard-wrap prose at a fixed column. Let the reader's client wrap long lines. Keep hard line breaks only where Markdown structure requires them (headings, table rows, list-item boundaries, fenced code blocks, which stay verbatim). This keeps diffs to whole-paragraph changes instead of reflow noise.
- **Skills are shared across harnesses by a two-way symlink shim, because the three harnesses scan skill roots to different depths.** Hermes owns the real tree at `/opt/data/skills` and nests it by category (`mlops/inference/vllm`). Verified against the pinned CLIs: **Codex** (`$CODEX_HOME/skills` plus `~/.agents/skills`) and **OpenCode** (`~/.agents/skills`, `~/.claude/skills`, and `skills.paths`) both walk `**/SKILL.md` recursively *and* follow a symlinked root, so one root symlink covers them; **Claude Code** scans its root exactly **one level deep** — a skill at `<root>/<category>/<name>/SKILL.md` is never found — but it *does* follow symlinks, including into a skill's `references/` support files. So `charts/agent/templates/shared-skills.yaml` **publishes** `~/.agents/skills` as a single root symlink and `~/.claude/skills` as a flat farm of per-skill symlinks keyed on each skill's leaf directory name. Don't "simplify" the farm into one symlink — Claude Code would silently see zero categorized skills. The farm skips `references`/`templates`/`assets`/`scripts` packages (a preserved `SKILL.md` in there is documentation, not a skill — `agent/skill_utils.py:is_skill_support_path`), never overwrites a real directory a harness created itself, and prunes links whose target was renamed or deleted. The same script also **adopts** in the other direction: a real directory in the Claude farm is a skill some other harness authored, and it gets linked into `/opt/data/skills/harness-authored/` so it reaches Codex and OpenCode via `~/.agents/skills` and appears in Hermes' index. Adoption is not optional cleanup — OpenCode runs with `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS=1` (both roots are the same tree, so it would otherwise warn once per shared skill), which means without adoption it never sees a Claude-authored skill at all. The publish walk prunes the adopt category so the two halves can't form a symlink loop. `skills.external_dirs` is set to Claude's root as well, and is load-bearing for a *different* reason than visibility: it makes `is_external_skill_path()` true for adopted skills so Hermes' curator treats them as externally owned instead of autonomously rewriting or archiving another harness's file. Scope `external_dirs` to `.claude/skills` only — Codex ships a vendored `.system/` tree (`imagegen`, `skill-creator`, …) that would otherwise be imported as user skills, and OpenCode's own skills are compiled into its binary. The script runs in `seed-data` at boot and again as a Hermes `post_tool_call` hook matched on `skill_manage` (hence `hooks_auto_accept: true`, since every agent entrypoint here is headless and cannot answer the first-use consent prompt), so a skill created mid-session publishes without a pod restart; it prints `{}` on stdout because that hook's wire protocol parses stdout as JSON and warns on anything else. Both scripts live in the **image** at `/usr/local/bin` (`images/hermes/skills-scripts/`, COPYed by the Dockerfile beside the patches layer), not in a mounted ConfigMap: they are agent-image behaviour rather than cluster config, and a ConfigMap costs four wiring points each (init-container mount, agent-container mount, volume list, `restart-job.yaml`) that fail silently if one is missed. The tradeoff is that editing one now needs a tag bump and a rebuild, not just `./vicegerent install`. **Publishing by symlink means a peer harness can destroy the canonical skill.** A farm entry is a symlink into Hermes' real tree, and `rm -rf <entry>/` or `rm -rf <entry>/*` — with the trailing slash or glob — recurses *through* the link and deletes the real content, silently, exit 0 (`rm -rf <entry>` without the slash, and `find -delete`, correctly remove only the link). Most skills are recoverable from the image, but an agent-authored one exists only on the `data` PVC, which `_sandbox.tpl` lists in `backup.velero.io/backup-volumes-excludes` and so is **not** in the nightly Velero backup. `snapshot-skills.sh` therefore commits the tree to a local bare repo at `/opt/data/.skills-snapshots.git` at boot and after every `skill_manage`; restore with `git --git-dir=/opt/data/.skills-snapshots.git --work-tree=/opt/data/skills checkout -- .`. The git dir is deliberately outside the tree (not `git init` in place) so no `.git` artifact lands where a harness walks, and transient bookkeeping (`.usage.json`, `.curator_state`, `.hub/`) is excluded via `info/exclude` since it is rewritten on every skill read; `.archive` is kept, because a curator-archived skill is exactly what is worth recovering. Regression tests: `images/hermes/patches/tests/test_shared_skills_sync.py`, `test_skills_snapshot.py`, and `test_skills_scripts_baked.py` (no Hermes install needed).
- **`hermes dashboard` and `hermes serve` do not register shell hooks upstream; patch `0042` fixes that.** `hermes_cli/main.py`'s `_prepare_agent_startup()` returns early unless the subcommand is in `_AGENT_COMMANDS` (`None`/`chat`/`acp`/`rl`) or matches an `_AGENT_SUBCOMMANDS` entry (`cron run|tick`, `gateway run`, `mcp serve`). `dashboard` and `serve` are in neither, so `register_from_config()` never runs and **every** config-declared `hooks:` entry is a silent no-op for the desktop app's backend — even though those commands do run full agent turns and fire the hook sites. The failure is invisible from the outside: `hermes hooks doctor` validates config, allowlist, and script health, not whether the *running* process registered, so it reports all-green while nothing fires. If a hook works under the gateway but not in the desktop app, this is why — check the patch is still applied before debugging anything else.
- **CiliumNetworkPolicy DNS and connection rules are two separate layers that must both list a destination.** A `toEndpoints`/`toFQDNs` rule permits the *connection*; a DNS `matchName` under `rules.dns` permits *resolving* that hostname in the first place. Adding one without the other either silently blocks a workload that already had connection access (DNS missing) or does nothing (connection missing). Also: `matchPattern` does not cross `.` label boundaries — a single `*` substitutes exactly one DNS label, so `*.svc.cluster.local` does not match two-label service names like `egress-proxy.egress-proxy.svc.cluster.local` (cilium#22081). Prefer exact `matchName` per real hostname over wildcards for in-cluster service DNS. When editing egress policy for a workload, check both its `toEndpoints`/`toFQDNs` rules and its DNS `matchName` list for every hostname it actually needs. **Corollary — a `matchName` allowlist only works if the resolver actually queries that exact name.** With the k8s default `ndots:5`, a Pod resolves a name with fewer than five dots (e.g. the 4-label `agentgateway-proxy.agentgateway-system.svc.cluster.local`) by trying the search domains *first* — emitting `…svc.cluster.local.<search-domain>` names that are not in the allowlist and get dropped. glibc (hermes/CPython) tolerates the dropped attempts and falls through to the absolute name; a musl resolver (the static `codex` binary) returns `EAI_AGAIN` ("failed to lookup address information: Try again") and the connection never happens. The agent Sandbox sets `dnsConfig.options ndots:1` (`charts/agent/templates/_sandbox.tpl`) so every FQDN destination is queried absolutely first — keep that in place whenever the DNS egress list is exact-`matchName`.
- **MCP authorization layering** — agentgateway is the single ingress gate for MCP traffic (routing, auth, mTLS to the host vMCP). Two separate concerns sit on top: *tool selection* (which tools an agent can see/call) and *argument-level authorization*. Tool selection is done upstream in ToolHive's vMCP (`aggregation.tools` in `toolhive-servers.json`) so operators can scope a backend by editing that file and restarting the host stack; agentgateway can also enforce a per-tool allowlist itself, and a corporate/centralized deployment would put it there instead — which place owns it is a policy choice, kept in ToolHive here for developer flexibility. A backend's own native flags/env vars are never used to narrow its tool set, only to force read-only mode or expand its own surface — see `host/mcp/README.md`'s "The 17 backends" section for the convention and examples. Argument-level authz is the `mcp-cerbos-shim` + Cerbos guardrail on the `vmcp` backend, a deny-by-resource guardrail (FailClosed on `tools/call`) that currently blocks: reading Kubernetes **Secrets**; reading the OpenSearch Grafana datasources; any **Elastic** (Kibana Agent Builder) data-access call whose target index/datastream matches a blocked token in `${elasticDeniedIndexPatterns}` (matched by substring against every index-bearing arg — `index`/`indices`/`pattern`/`indexPattern`/ stream `name` — plus the `execute_esql` query text, surfaced as a `targets` list by the `elasticTargetsAttr` shim helper; reads that never name a blocked index are unrestricted, and an index-less/wildcard search that dodges the token is a documented residual gap best closed by scoping the Elastic API key's own role); any **AWS** `call_aws` command (aws-api-mcp-server) that mints credentials/tokens/access or reads secret values — `READ_OPERATIONS_ONLY` does NOT block these (verified live: `eks get-token` returned a real Kubernetes bearer token, and the server even force-allows some credential minters), so `resource_aws.yaml` denies, by parsed `<service>/<operation>` (the `awsSecretReadAttr` shim helper tokenizes the CLI command, batch-aware), a hardcoded set of credential/access minters (`eks/get-token`, `sts/assume-role*`, `ecr`/`ecr-public`/`codeartifact`/ `codecommit` auth, `rds`/`redshift` DB tokens, `kms/decrypt`, `ssm/start-session`, `ec2/get-password-data`, `s3/presign`, …) and secret-value reads (`secretsmanager/get-secret-value`/`batch-get-secret-value`, `ssm/get-parameter*`) — defense-in-depth regardless of the read-only gate, with the profiles' own IAM permission sets as the airtight complement and the `IsWrite=false` long tail (env-var-bearing `describe-*`, bulk/wildcard enumeration) a documented residual gap; any **Jira** WRITE (create/update/transition/comment/link) targeting a project outside `${jiraAllowedProjects}` (by `project_key`, the project prefix of an issue/epic key, or an `epicKey`/`parent` reference smuggled inside `additional_fields`/`fields`' raw JSON — parsed by the `jiraFieldsAttr` helper, since that's a documented control being routed around via a side channel, not just an unmapped extra arg), or assigning an issue to anyone outside `${jiraAllowedAssignees}` (default `"*"`, i.e. unrestricted — there is no `reporter` field on this tool at all) — reads (`get_issue`/ `get_project_issues`/`get_transitions`) are unrestricted, mirroring Notion's read-everywhere/write-scoped model; any **GitHub** call targeting a repo outside the allowlist in `charts/cerbos-policies/policies/resource_github.yaml` (by `owner`/`repo`), writing directly to a protected branch (main/master/production), setting `reviewers` on a PR (request reviews by hand instead), opening a PR into a `${githubForkRequiredOwners}` repo from anything but a `${githubForkOwners}` fork, or opening/editing a PR against a repo that mandates a ticket-reference title or a change-ticket link in the body without one; any **Linear** `save_issue`/`save_project`/`create_issue_label` call whose team falls outside `${linearAllowedTeams}` (`charts/cerbos-policies/policies/resource_linear.yaml`) — `save_issue` and `save_project` each merge create+update, and a create always names its own team (`team`, or `addTeams`/`setTeams`), while an update that omits it gets the real team from a live `linear_get_issue`/`linear_get_project` lookup rather than falling through unchecked; `create_issue_label` carries a directly verifiable `teamId` when the label is team-scoped and needs no lookup, and `save_comment` is checked by the live assignee gate below; any **Alertmanager** `createSilence` call whose duration exceeds the configured cap, or `deleteSilence` call targeting a silence this agent didn't create (`charts/cerbos-policies/policies/resource_alertmanager.yaml` — live-resolved, see below; a silence's creator used to be unverifiable from the call args alone, which is why the ownership deny was removed once before, but `createSilence` now force-stamps a fixed `createdBy` and `deleteSilence` resolves it live, making the check real again); any **Alertmanager** `getAlerts` call with no `filterLabel` (`charts/cerbos-policies/policies/resource_alertmanager_alert_query.yaml` — an unfiltered query times out, and this operator only pages on critical severity, so an unfiltered call is never the right call); any **PagerDuty** `manage_incidents` call that changes anything other than status=acknowledged/resolved (`charts/cerbos-policies/policies/resource_pagerduty.yaml` — an allowlist of the `incident_ids`/`status` shape, so a field the helper has never heard of is out of scope too, rather than a denylist of `urgency`/`escalation_level`/`assignement`); any **Notion** `update-page` call that sets `command: replace_content` or `allow_deleting_content: true` (`charts/cerbos-policies/policies/resource_notion.yaml` — `create-pages` is denied outright on any parent other than the Scratchpad folder, with a message naming the correct `page_id`; it used to be silently force-rewritten instead, which discarded whatever parent the agent intended and taught it nothing, so it kept guessing on every future call); any **Firecrawl** `firecrawl_interact` call that carries raw `code` to execute in the browser session (`charts/cerbos-policies/policies/resource_firecrawl.yaml` — `prompt`-only natural-language interaction remains allowed); any **GitLab** call — reads included, same read-scoped posture as `github_repo` — targeting a project outside `${gitlabAllowedProjects}` (`charts/cerbos-policies/policies/resource_gitlab.yaml`; the shim resolves any spelling GitLab accepts (numeric id, group/project path, percent-encoded, any casing — all four verified live to hit the same project) to the project's numeric id via a live `get_project` lookup before Cerbos matches, so an operator lists ONE canonical value per project rather than enumerating forms, and both sides are lowercased as a fallback; also checked against `target_project_id`, the second project `create_issue_link`/`create_merge_request` carry, so an allowlisted project can't carry a write landing outside it), pointing a merge request at a protected branch via `target_branch`, setting `reviewer_ids`/`assignee_ids` on a merge request (issue `assignee_ids` is deliberately unrestricted), or updating a merge request it didn't author; and any **Tavily/Firecrawl** crawl/fetch/monitor call whose target resolves to an internal address — `host.docker.internal`, RFC1918/loopback/link-local, the cloud metadata IP, a `*.svc.cluster.local` name — or a crawl over the `limit`/`depth`/`breadth` caps (`charts/cerbos-policies/policies/resource_webcrawl.yaml`; these URLs are agent-instructable rather than user-typed, so this is a real SSRF vector, and a `monitor_*` target is a standing probe rather than a one-shot fetch). GitLab's three git file/branch-write tools plus `merge_merge_request` were removed from the allowlist rather than policed (the bot has direct SSH access to gitlab.hahomelabs.com), as was every note/thread/discussion/draft-note WRITE tool — the operator does not want the bot leaving any comment text under their identity, the same call made on GitHub, and removing the capability is strictly stronger than gating it (the note READ tools stay); `mark_todo_done`/`mark_all_todos_done` carry no `project_id` and are the documented unscopable residual gap. The shim mapping and Cerbos rules deny protected resources; they are not the place to permit or block a tool outright — that's the tool-selection layer above. A tool's mapping can also carry a `force` block — a literal, unconditional argument rewrite applied only after Cerbos allows (GitHub `create_pull_request`/`update_pull_request` force `draft: true` so every agent-opened PR stays a draft; Alertmanager `createSilence` forces `createdBy` to `${alertmanagerCreatedBy}` so `deleteSilence`'s ownership check has a real value to verify against) — or a `forceFrom` expression, for an override that must be DERIVED from the call's own args rather than being a constant. GitLab's draft rule needs the latter: GitLab has no draft field (verified live — `draft: true` is silently ignored) and derives draft status from the merge request's TITLE, so `create_merge_request`/`update_merge_request` use `forceFrom: gitlabDraftTitleForce(args)` to prefix the incoming title with `Draft: `. A literal `force: {draft: true}` copied from the GitHub side was a silent no-op, and every agent-opened MR shipped ready-for-review until it was replaced. This is a mutation, not a deny; it never overrides a Cerbos denial. See `images/mcp-cerbos-shim/README.md` ("Authorization Layers"). Six of these checks are **live-resolved**, not argument-only — closing the gap that let Hermes once hallucinate a GitHub PR number and edit someone else's PR description (a hallucinating agent has no reason to lie about ownership, it just targets the wrong id, so an arg-only check can't catch it): before Cerbos runs, the shim resolves the resource's REAL current state via a live lookup back through vMCP (`internal/upstream`, the same mechanism the Notion ancestry/Linear-team/PagerDuty-service gates already used) and injects it into `res.Attr`, letting Cerbos's own rule decide. A GitHub `update_pull_request`/ `update_pull_request_branch`/`request_copilot_review` call is denied unless the PR's real author (`pull_request_read`) matches `${githubUsername}` (`deny-not-own-pr`); a GitLab `update_merge_request` call is denied unless the MR's real author (`gitlab_get_merge_request`, selected by whichever of `merge_request_iid`/`source_branch` the call itself used) matches `${gitlabUsername}` (`deny-not-own-mr` — the MR note/thread/discussion/draft-note tools are deliberately NOT gated, since reviewing others' merge requests is why they're allowlisted); a Jira `update_issue`/`add_comment`/`transition_issue` or Linear `save_issue` update/`save_comment` call that doesn't itself carry an assignee/team is denied unless the ticket's CURRENT assignee (`jira_jira_get_issue`/`linear_get_issue`) matches `${jiraAllowedAssignees}`/`${linearAllowedAssignees}` (the existing `deny-assignee-outside-allowed` rules — no new Cerbos rule needed, just a populated attr); a Notion `update-page`/`create-comment` call is denied unless the page's real author (a `notion-fetch` + creator-filtered `notion-search`) matches `${notionUserId}` (`deny-not-own-page`, a boolean `pageAuthorMismatch` attr — a semantic search match, since `notion-fetch`'s own output carries no author field, so this is fail-closed-**safe**: a false negative denies a legitimate write, never falsely allows a non-owner's edit); and an Alertmanager `deleteSilence` call is denied unless the target silence's real `createdBy` (a `getSilences` list-then-filter lookup, since no single-silence-get tool exists) matches `${alertmanagerCreatedBy}` (`deny-not-own-silence`) — the counterpart `createSilence` call force-stamps that same `createdBy` value via `charts/mcp-cerbos-shim/files/mapping.yaml`'s `force` block (Alertmanager's own `createdBy` arg is caller-supplied and optional, unlike the other three's externally-authenticated identities, so a real value has to be established at creation time before deletion can check it), so the two halves stay in sync by construction; silences created before this gate shipped still carry the old default `createdBy` and are undeletable via MCP until they expire naturally (non-security-relevant). All six fail closed on an unconfigured gate or lookup error. An unassigned Jira/Linear ticket is a legitimate empty rather than a lookup failure, but it is no longer allowed either: the gate marks a definitively-resolved lookup with `assigneeVerified=true`, and `deny-write-unassigned-issue` denies a write to a genuinely-unassigned ticket — an absent attr (the call supplied its own verifiable assignee, so no lookup ran) still falls through to the has()-guarded allow. See `images/mcp-cerbos-shim/README.md` ("Live-Resolved Ownership Gates"). A third, orthogonal concern is **content moderation** — content *quality*, not authz: the shim can send free-text args of write-shaped calls (Notion/Linear/GitHub/GitLab/Jira/ PagerDuty) through OpenAI's Moderations endpoint before Cerbos runs, denying on a flagged result. Toggled per-machine (`contentModeration` in `values.yaml`), and — unlike every other gate above — fails OPEN on a moderation-service error, since a classifier outage is a service degradation, not an authz gap. See `images/mcp-cerbos-shim/README.md` ("Content Moderation"). A fifth concern is **prompt-injection detection** — a two-stage gate on tool READ results (Firecrawl/Tavily/Notion/Jira/GitHub/GitLab reads etc.) via `CheckResponse`: a broad regex prefilter gates a stage-2 LLM-judge call, and a confirmed detection DENIES the call (deny only, never a partial strip), toggled per-machine (`promptInjectionDetection` in `values.yaml`). See `images/mcp-cerbos-shim/README.md` ("Prompt Injection Detection").

## Command Approval System

Hermes runs with `approvals.mode: smart` (the default in the agent chart's rendered config, `charts/agent/templates/_helpers.tpl`). Before executing a shell command, the approval pipeline runs in this order:

1. **Hardline block** — unconditional, nothing bypasses it. Covers catastrophic commands (`rm -rf /`, disk formatters, fork bomb, system halt). Defined in `tools/approval.py`.
2. **Silence list** — operator-configured patterns dropped before any LLM sees them. Baked into `charts/agent/templates/approval-policy.yaml` (ConfigMap `<agent>-approval-policy`, mounted read-only at `/opt/hermes/approval-policy.yaml`). Tirith findings and uncancellable patterns (Hermes config escalation, credential writes, self-termination) are never silenced.
3. **Tirith** — static security scan. Findings that survive the silence list go here.
4. **Smart approval (haiku)** — aux LLM assesses remaining warnings. Auto-approves low-risk, auto-denies genuinely dangerous, escalates ambiguous to the user.

**Why not `approvals.mode: off`?** That skips steps 3 and 4 entirely — tirith never runs. `mode: smart` + a well-tuned silence list gives zero friction on known-benign patterns while keeping real detection on novel ones.

**Why not `TERMINAL_ENV=docker`?** The docker backend requires a Docker socket, which does not exist in the sandbox. Setting it removes the `terminal` tool from the schema entirely.

**To add a pattern to the silence list:** edit the silence list in `charts/agent/templates/approval-policy.yaml`, open an MR, and re-run `./vicegerent install` once merged. Reloader watches the ConfigMap via `restart-job.yaml` and rolls the pod automatically when its content changes. Do not silence tirith findings or uncancellable patterns — those are enforced in code regardless.
