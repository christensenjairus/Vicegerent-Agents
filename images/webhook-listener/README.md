# Webhook listener

`webhook-listener` is Vicegerent's shared, in-cluster ingress for provider webhooks. A separate `cloudflared` workload opens one outbound Cloudflare Tunnel and forwards it to the listener's ClusterIP Service. The listener verifies each request and routes `/webhooks/<agent>/<route>` through the dedicated webhook scrubber to that agent's fixed ClusterIP Service on port 8644.

## Trust boundary

The listener is the only workload that receives provider signing material. Its Deployment mounts the shared `webhooks/vicegerent-webhook-secrets` Secret read-only and reads the route-derived `<agent>__<route>` key for every request, so Secret rotation is observed without placing the value in an environment variable or restarting an agent. The Cloudflare tunnel credentials live in `webhooks/vicegerent-cloudflared-credentials` and are mounted only into the separate `cloudflared` Deployment, so the workload holding signing material never sees tunnel credentials and vice versa.

The tunnel is locally managed: `cloudflared` reads its ingress mapping from an in-repo ConfigMap that forwards only the configured public hostname to the listener's ClusterIP Service and answers everything else with 404. A Cloudflare account compromise therefore cannot repoint the tunnel at another in-cluster target; changing where public traffic lands requires cluster access and a reviewed chart change. The tunnel credentials are scoped to this single tunnel and cannot create endpoints or change DNS.

After a signature succeeds, the listener strips every recognized credential header and forwards the original method, ordinary headers, query string, and raw body using an explicit `WEBHOOK_FORWARD_PROXY` transport. Stripping matches by shape rather than an exact denylist, and covers the whole `Cf-Access-` prefix: those headers are minted by the Cloudflare edge to authenticate the caller to Cloudflare, so an agent must not be able to read or replay them. The remaining `Cf-` headers are delivery telemetry (client IP, ray ID) and reach the agent. Targets are validated at startup against the exact `http://<agent>-webhook.agent-sandbox.svc.cluster.local:8644/webhooks/<route>` shape, preventing a ConfigMap change from turning the listener into an arbitrary-network relay. The dedicated proxy redacts recognized secrets before forwarding and optionally screens the redacted body for prompt injection.

Both workloads run as uid/gid 65532 with a read-only root filesystem, no capabilities, and no service-account token. Cilium permits `cloudflared` to resolve its edge and listener names, connect to `region1.v2.argotunnel.com` and `region2.v2.argotunnel.com` on port 7844, and enter only the listener's port 8081. Both 7844 protocols are open because `cloudflared` negotiates its own edge transport: it picks QUIC over UDP, and HTTP/2 over TCP is the fallback if UDP egress breaks. It cannot resolve or connect to the dedicated webhook proxy. The listener accepts port 8081 only from `cloudflared`, can resolve and connect to only `webhook-egress-proxy:8080`, and has no Cloudflare-edge or direct-agent egress. Each agent's reciprocal policy accepts port 8644 only from that proxy and only for the agent's configured HTTP route paths. Agent sandboxes cannot reach the listener or dedicated proxy, while their ordinary egress proxy cannot reach agent webhook ports. `cloudflared` serves nothing to the cluster, so its policy asks Cilium for ingress default-deny explicitly; Cilium enforces a direction only when a policy carries rules for it. Kubernetes probes use a separate loopback-only endpoint for the listener and `cloudflared tunnel ready` for the tunnel, while `/healthz` is also served on the public listener for tunnel diagnostics. Both Deployments use the `Recreate` strategy so configuration or credential rollouts do not briefly overlap replicas.

Each configured-route delivery logs an outcome, agent, route, provider, status, request byte count, and duration. Vector collects these lines into VictoriaLogs, along with the `cloudflared` container's own edge-connection logs, which is where transient QUIC churn is visible. Its scope names each container explicitly, so both workloads are listed there. Request bodies, provider signature headers, and signing secrets are never logged.

## Routing configuration

The chart renders `/etc/vicegerent-webhooks/routes.json` from each enabled `agents[].webhooks.routes` entry, and a separate `cloudflared` ConfigMap from `webhooks.publicUrl` and `webhooks.tunnelId`. The listener itself never sees the public hostname, so both of those values are validated beside the tunnel ConfigMap that consumes them; the all-zero UUID is rejected there as well, so a copied example fails to render rather than pinning `cloudflared` to a tunnel that does not exist. The external provider, route-derived Secret file, and fixed target remain in this listener ConfigMap. The agent chart removes `provider`, injects only `trusted_proxy: true` plus delivery/prompt metadata into Hermes, and rejects attempts to set internal signing fields directly.

Supported providers:

- `pagerduty`: HMAC-SHA256 of the raw body, accepting any valid `v1=` candidate in `X-PagerDuty-Signature` during rotation.
- `github`: HMAC-SHA256 of the raw body in `X-Hub-Signature-256` as `sha256=<hex>`.
- `gitlab`: constant-time comparison of `X-Gitlab-Token`; GitLab's native protocol authenticates the token but does not bind the body cryptographically.
- `svix`: HMAC-SHA256 of `<id>.<timestamp>.<body>`, supporting raw and `whsec_` base64 secrets plus multiple rotation signatures.
- `generic-v2`: HMAC-SHA256 of `<timestamp>.<body>` in `X-Webhook-Signature-V2`.
- `alertmanager`: constant-time comparison of the credential in the `Authorization` header. Alertmanager signs no payload, so this authenticates the sender without binding the body; the header is stripped before forwarding so the credential never reaches the agent.

Svix and generic V2 sign a timestamp and reject one outside a five-minute window. Because their signature is bound to that window, both are additionally single-use: the listener remembers each accepted delivery per agent and route (its generic V2 signature, or Svix's `Svix-Id`) for twice the tolerance, which is the full span in which one signature verifies, and answers a duplicate with 403 before forwarding. A delivery releases its entry only when the connection to the dedicated proxy could not be established, which is the one error proving nothing reached the agent; after that the agent may already have acted, so the entry stands and the provider's retry is answered with 403 rather than delivered twice. Because the connection is proxied, that failure arrives wrapped in a `proxyconnect` error, so the classifier walks the error chain instead of inspecting only its outermost layer. A proxy restart is the ordinary case and is classified as undelivered even when the listener still holds a pooled connection to the old process: the transport discards the closed connection, redials, and reports the refusal. Only a delivery caught in the instant that connection closes fails ambiguously instead, so it keeps its key and the provider's retry is answered with 403. That trade is deliberate: it can drop a single delivery, where the alternative risks acting on one twice. The proxy can also answer a delivery itself: it synthesizes a 502 when it cannot complete the request to the agent, so the listener reports that as a failed delivery with reason `upstream_bad_gateway` and answers the provider its own 502 instead of relaying the proxy's error page, which names the proxy and the in-cluster address it could not reach. Such a delivery keeps its replay key, because the proxy renders a connection it never opened and one it lost after writing the request as the same untagged 502. An agent that answers 502 itself is reported the same way; every other status is the agent's own answer and reaches the provider unchanged. The cache is a single bound of 10,000 keys shared by every agent and route, and it fails closed when full: deliveries are answered with a retryable 503 rather than a 403, so sustained traffic above roughly 17 timestamped deliveries per second stalls every route until the window drains. The remaining providers do not sign a timestamp, so their deliveries stay replayable and a bounded cache could not reject them; the forge or provider is the boundary there.

Payloads are capped at 1 MiB. Unknown agents, unknown routes, disabled routes, and unsupported methods return the same 404 shape so the endpoint does not expose route membership.

## Build and test

The image name and immutable tag live in `Makefile`. `make check` is CI parity and runs formatting, `go vet`, and the full unit/proxy suite.

```bash
make check
make image
make release
```

The tests cover fixed known-good signatures, wrong secrets, body tampering, expired timestamps, single-use enforcement across the whole signature window and per agent, retry after an undelivered forward and refusal after an ambiguous one (both driven through the real forward transport, since the proxied error shape is what the classification turns on), a proxy-generated 502 answered as a failed delivery instead of being relayed while an agent's own 500 is relayed unchanged, cache saturation, rotation formats, credential-header stripping alongside `Cf-` telemetry preservation, body/query preservation, an explicitly pinned forward proxy, the accepted wildcard binds, indistinguishable unknown routes, failure-before-forwarding, and cross-agent target rejection. Repository-level Helm, scrubbing, prompt-injection, and Cilium assertions live in `scripts/validate-webhook-ingress.py` and `scripts/test-scrub-patterns.py`.
